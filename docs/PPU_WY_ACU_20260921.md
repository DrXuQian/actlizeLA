## State: equal matrix work, much more expensive delivery

Both implementations iterate over 32 C64 chunks and compute `U - W @ H`
followed by the decayed `H + K.T @ Vnew` update. Both launch 128 V32 CTAs.
FLA also keeps the chunk recurrence sequential; it is not scanning time in
parallel while WY is serial.

| State metric | WY | FLA |
|---|---:|---:|
| BF16 tensor instructions | 524,288 | 524,288 |
| Executed instructions, total | 34,556,288 | 10,040,320 |
| Threads / CTA | 64 | 128 |
| Achieved warps / CU | 3.55 | 7.09 |
| Registers / thread | 244 | 256 |
| Dynamic shared bytes / CTA | 37,120 | 50,432 |
| Stack bytes / thread | 0 | 0 |
| Register / shared block limits | 8 / 7 | 4 / 5 |
| Global store instructions | 802,816 | 102,400 |
| KVD-interface global-store bytes | 822,083,584 (784 MiB) | 102,760,448 (98 MiB) |
| DRAM bytes, all traffic | 101,721,984 | 101,320,832 |

The native MMA count closes exactly:
`128 CTAs * 32 chunks * 2 warps * (32 WH + 32 KTV) = 524,288`.
Thus the 5.213x state-time gap is **not five times as many matrix products**.
It also is not eight times the HBM payload: DRAM bytes differ by only 0.4%.

The state launch does not fill either resource envelope. In WY,
`128 / 72 * 2 = 3.556` warps/CU predicts the achieved 3.55; FLA uses four
warps/CTA and achieves 7.09. Calling WY "register-limited at 244 registers"
would miss that only ~1.78 blocks/CU are launched, far below its measured
7-block shared-memory limit. Increasing threads alone is not a fix: the
state ownership / WH reduction or redistribution must change consistently.

### A byte ledger that reproduces the observed store counter

`result_coord(lane, slot)` gives native C coordinates:

```
row = lane / 4 + (slot / 4) * 8
col = lane % 4 + (slot % 4) * 4
```

At a fixed slot, a warp scatters BF16 stores over eight rows, writing only
four adjacent values (8 bytes) in each row. It then repeats for the remaining
slots. The shipped assembly contains scalar `vmem.st.b16`, not packed
vector epilogues. The final FP32 stores are likewise `vmem.st.b32`.

An analysis-only host program includes the **shipping coordinate function**,
checks all 256 lane/slot pairs against actual actlize MMA C traits, and
enumerates the addressed 128-byte lines. This footprint matches the uploaded
KVD counter exactly, including the store-instruction denominator:

| Source write | Useful bytes | Warp store instructions | Addressed-line bytes |
|---|---:|---:|---:|
| Incoming BF16 H snapshots | 32 MiB | 524,288 | 512 MiB |
| BF16 Vnew | 16 MiB | 262,144 | 256 MiB |
| Final FP32 H | 2 MiB | 16,384 | 16 MiB |
| Total | **50 MiB** | **802,816** | **784 MiB** |

The observed transaction counter is 12,845,056 units of 64 bytes. The
128-byte-line enumeration is a calibrated description of this access
pattern, **not an assertion that every PPU transaction is 128 bytes**, and
not a DRAM-traffic prediction. Omitting one native fragment slot makes this
ledger fail the immutable ACU denominator/byte anchors (negative control).

The corresponding code sites are `ws.snapshots[...]`, `ws.vnew[...]`, and
`final[...]` in `gdn_wy_state`. Source/assembly and the measured counter agree:
there is an established delivery inefficiency, not a speculative cache story.

The direct `ws.u[...]` read has the same scattered scalar layout. Its
262,144 warp loads account for 256 MiB at the KVD interface; the gate loads
add 1 MiB, totaling the observed **257 MiB** of ordinary global-load traffic.
WY uses cp.async for W/K, but not for these U scalar reads. FLA's U transport
is on a different path, so comparing only its 2 MiB ordinary-load counter
to 257 MiB would be incomplete: FLA has 166.328 MiB of global-to-shared traffic
versus WY's 128 MiB. Its entire delivery ledger, not one selected counter,
is the comparison object.

State memory-dependency counters are also consistent with different paths:
WY global-load dependency 0.78 versus FLA 0.06, while FLA shared dependency
is larger (1.10 versus 0.20). These are per-issued-instruction ratios, not
percentages of wall time; their sum cannot apportion the 375.6 us difference.

## Other stages are not already aligned

- Prepare BF16 counts match: WY 344,064, FLA KKT+WU 81,920+262,144.
  WY TF32 counts are 98,304 versus FLA's 32,768. Our FP32 diagonal solve /
  high-residual block-merge strategy is a separately identifiable difference.
  Its precision contract cannot be dropped merely to match an instruction count.
- Prepare uses 47,315,968 executed instructions versus 17,228,800 for FLA's
  prefix+KKT+WU. The native scalar W/U output stores reproduce another
  amplification: 32 MiB useful W/U creates 512 MiB KVD write traffic, plus
  0.25 MiB of gates (observed total 512.25 MiB).
- Output also has equal BF16 count 524,288. WY emits 18,479,104 total
  instructions versus 9,166,848 and writes 256 MiB at KVD for a 16 MiB
  BF16 output; FLA writes 16 MiB. This repeats the direct native-fragment
  scalar-store problem. WY uses 128 threads versus FLA's 256 for this stage.

   Check actual emitted loads/stores as well as ownership; mere shape equality
   cannot prove that native-fragment traffic has been repaired.

3. Reuse the proven epilogue delivery primitive in prepare/output, then decide
   whether fused preparation still pays. Keep solve-precision changes separate.

No kernel implementation, tolerance, reset threshold or production routing
changed for this analysis. All existing device correctness and same-protocol
timing gates remain prerequisites for promoting a candidate. The first target
is the state gap; no unmeasured speedup or final FLA parity is promised.
