## Idle-window timing

Shape: **B1,T2048,Hk16,Hv32,Dk128,Dv128,C64**, BF16 gate/Q/K/V/beta,
zero initial state, output and FP32 final state returned. One fused forward
kernel is intended by the launch graph; NCU trace verification remains blocked.

Protocol: five warmup graph replays;11 event samples;20 forwards per graph.
Numbers are microseconds per forward in a CUDA Graph, not Python API wall time
or ACU durations. Prepared input addresses are reused; no cold-cache claim.

| Dependency used to build CUDA SM90a code | g=-0.1 median [range], us | g=-1.0 median [range], us |
|---|---:|---:|
| CUDA CUTLASS4.3.2 | 352.850 [349.669,353.410] | 350.253 [349.864,351.550] |
| PPU CUTLASS3.6.0 source-check | 325.987 [325.261,326.616] | 325.680 [325.102,326.843] |

Each admitted arm has42 process/telemetry samples, three empty-process/zero-
utilization samples before initialization, and only that arm's process observed
afterward. Sampling interval0.2s plus explicit checks around measurement.
This is monitoring, not scheduler-enforced exclusivity: a shorter foreign job
could evade sampling, so an operator-reserved window is still preferable.
Telemetry includes idle345MHz and active1755MHz; no frequency normalization
or locked-clock claim is made.

An earlier fourth-arm attempt and its retry were blocked by the idle gate.
Other `single-launch`/Python GPU jobs were then observed. Those jobs were not
stopped. After the GPU returned to idle, all four final arms were rerun in
fresh output directories; earlier partial timings are not substituted into
this table. Concurrent-PID, unreadable-process-list and nonzero-idle-utilization
negative controls fail rather than silently admitting timing.

This is an initial integration baseline, **not a fast-kernel verdict**. CUDA12.8
reports spills and WGMMA serialization due to register pressure; these remain
open performance issues. Grid=B*Hv=32 also cannot occupy every one of114 SMs.
No FLA baseline was installed/measured on this host, so there is no same-host
FLA ratio and no claim of meeting1.5x. The two dependency builds were not sampled
in a randomized interleaved A/B protocol; the table is descriptive, not a claim
that a PPU device is faster than a CUDA device. Both ran on the same H800.

## Reproduction

Build as documented in `SM90_FUSED_GDN.md`, retaining `build.json` beside each
extension. Run the complete physical-Hopper suite serially:

```bash
python tests/run_sm90_hopper_cases.py --backend cuda_sm90 \
  --extension /workspace/your-cuda-build/_gdn_fused_sm90.cpython-312-x86_64-linux-gnu.so \
  --out /workspace/gdn-hopper-cuda-cases

python tests/run_sm90_hopper_cases.py --backend ppu17 --source-check \
  --extension /workspace/your-ppu-source-build/_gdn_fused_sm90.cpython-312-x86_64-linux-gnu.so \
  --out /workspace/gdn-hopper-ppu-source-cases
```

Only after the device is idle:

```bash
python benchmarks/bench_sm90_hopper.py --backend ppu17 --source-check \
  --extension /workspace/your-ppu-source-build/_gdn_fused_sm90.cpython-312-x86_64-linux-gnu.so \
  --gate=-0.1 --out /workspace/gdn-hopper-ppu-source-perf
```

Use `--gate=-1.0` and a fresh output directory for the other regime. These
repeated hardware runners are **not single-call simulator inputs**; use
`tools/run_sm90_gdn.py` separately for that contract.
