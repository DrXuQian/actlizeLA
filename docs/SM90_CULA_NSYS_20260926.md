# H800: original cuLA versus scalar fused GDN, nsys kernel time

## Verdict

On the admitted scalar-gate workload, our incumbent is faster than the original
cuLA C++ Hopper path. This is physical **H800** evidence, not PPU1.7 device
performance, not general per-channel KDA, and not an FLA comparison.
No production kernel, default, numerical threshold or routing changed.

Same H800 PCIe, B1/T2048/Hqk16/Hv32/K128/V128, BF16 Q/K/V/beta/g,
zero initial state, FP32 final state. Scalar natural-log g is broadcast to K
on CPU for cuLA: identical quantized gate values, different public gate layout.
Every arm uses the same CPU-generated Q/K/V/beta values and recurrence oracle.

Times below are the **median of the per-forward sum of all GPU kernel
durations** from nsys, microseconds. Twelve interleaved calls per arm per gate.
Observed ranges are in brackets; neither comparison has overlapping ranges.

| Gate | Original cuLA C++ full forward | Ours, CUDA CUTLASS4.3.2 | Ours, PPU CUTLASS3.6 CUDA source-check |
|---|---:|---:|---:|
| -0.1 | 447.249 [445.792,450.304] | 354.801 [353.440,356.672] | 332.704 [329.856,334.688] |
| -1.0 | 447.376 [445.952,448.288] | 354.864 [353.408,356.096] | 333.312 [330.048,337.824] |

cuLA/ours speed ratio: **1.261x** for the CUDA incumbent;
**1.344x / 1.342x** for the PPU-fork CUDA source-check incumbent. The latter
still runs NVIDIA SM90a machine code on H800. It is not native PPU code.
Source, dependency version and compile flags differ between packages; these
ratios do not isolate a CUTLASS-version effect or the cost of serialization.

## Complete GPU accounting

Each original cuLA call actually contains three kernels, not one:

| Component (individual-kernel median, us) | g=-0.1 | g=-1.0 |
|---|---:|---:|
| Original vector gate chunk-local prefix | 22.960 | 23.216 |
| Final-state zero initialization (`FillFunctor<float>`) | 1.536 | 1.584 |
| Original fused C++ KDA | 422.928 | 422.496 |

Each adapted call has exactly one fused kernel. Its scalar gate prefix is
inside that kernel; final state is fully written without a preceding fill.
These component medians need not sum to the median of the per-call sum.
All **120 kernels / 72 forward ranges** across the two reports are assigned
exactly once. No kernel was discarded by a name-based timing filter.

cuLA GPU first-activity-to-last-activity span is 509.472/621.744 us; internal
idle gaps have medians 62.032/174.784 us. These CPU-submission/profiling-sensitive
gaps are reported separately, **not included in the speed ratios above**.
Both our one-kernel arms have zero internal GPU gaps. No captured memcpy or
memset activity is omitted; cuLA's state clear is a real GPU kernel here.
The trace protocol uses synchronized eager calls, not the previous CUDA Graph
event timing. Do not subtract these times from old graph/API measurements.

## WGMMA: is the original also serialized?

Three different meanings must stay separate:

1. **Algorithm:** the original C++ SM90 path carries a recurrent state through
   chunks for each (sequence,value-head). That dependency is sequential;
   different heads and four warpgroup roles still operate concurrently.
2. **Source dependencies:** original `mainloop_kda_fwd.hpp` has five
   commit/`warpgroup_wait<0>` sites for Q@state, K@state, new-V, intra-output,
   and K@V. Our port retains those sites. TMA loading, auxiliary QK/KK and
   state/output roles use separate pipelines; this is not an entirely
   synchronous kernel. The generic launch bounds and register-budget function
   are also unchanged:512 threads, load24/state168+168/aux152 registers per
   thread in the respective runtime roles.
3. **Compiler:** compiling the **unmodified original** with its pinned
   dependency and its own `setup.py` flags also emits C7512 in **4/4**
   specializations: WGMMA serialization due to insufficient register resources.
   Original flags include `--register-usage-level=10` and `--use_fast_math`;
   their presence does not remove the warning. No claim is made that every
   WGMMA site is serialized, or that a particular fraction of time is caused
   by this warning. That requires a matched codegen/resource experiment.

Original selected BF16-beta/no-initial specialization:128 reported registers,
248-byte stack, ptxas476-byte spill-store /580-byte spill-load metrics. With
initial state:336-byte stack and668/1228. These are compiler resource metrics,
**not dynamic traffic counts**. Trace geometry of all three fused kernels is
grid32, block512,128 reported registers. Dynamic shared is232448 B original
versus167936 B in both scalar-gate incumbents. Do not infer active occupancy
from these resource numbers alone.

Thus the warning is reproducible in upstream, not evidence by itself that the
port broke asynchronous execution. Nor does being faster than this upstream
configuration mean the warning, spills or grid32 underfill are optimal.

Re-run with explicit paths in an **unused** output directory on an idle H800:

```bash
mkdir -p "$OUT" "$OUT/scratch"
TMPDIR="$OUT/scratch" "$NSYS" profile --trace=cuda,nvtx --sample=none \
  --cpuctxsw=none --capture-range=cudaProfilerApi --capture-range-end=stop \
  -o "$OUT/forward" "$PYTHON" benchmarks/profile_sm90_cula.py \
  --cuda-extension "$CUDA_EXTENSION" --ppu-source-extension "$PPU_SOURCE_EXTENSION" \
  --cula "$CULA_SOURCE" --out "$OUT" --gate=-0.1
"$NSYS" export --type sqlite --output "$OUT/forward.sqlite" "$OUT/forward.nsys-rep"
"$PYTHON" tools/analyze_sm90_nsys.py --sqlite "$OUT/forward.sqlite" \
  --receipt "$OUT/receipt.json" --out "$OUT/summary.json"
```

The next gate uses a new directory and `--gate=-1.0`. Capture range excludes
warmup/JIT/CPU oracle and post-run output copies. The parser rejects extra or
missing activities. See the [Nsight Systems capture-range documentation](https://docs.nvidia.com/nsight-systems/UserGuide/).
