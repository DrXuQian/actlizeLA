## Fast-exp2 experiment and recent command failures

The user-authorized arithmetic experiment is default-off and affects exp2
only, not global fastmath/FMA/division settings. Source `86c3ef6`, extension
`e72755a751ca7efab6236c3e7e7308b7dd1d9e33d18701f63478765bad868b2b`.
Across four actual native bodies it removes 64 underflow comparisons,
128 FMUL sites and 200 instruction positions per body, with unchanged
64 EX2 sites, matrix/TMA/barrier counts and 16/104-byte stack allocations.
The freshly rebuilt standard path is native-identical to its parent.

All 14 CPU-oracle cases plus two extreme-gate diagnostics pass the unchanged
2% output/state criterion. Ordinary fixtures also happen to match the parent
raw bits; that is not a universal exact-math claim. All eight graph screens
are unresolved; paired nsys does not show a consistent advantage. Keep
standard exp2 as the retained default; do not promote static code reduction
as a speed win.

The first attempt used a nonexistent CUDA device intrinsic, `__exp2f`.
That was **our implementation error**, not an environmental limitation. A
tiny two-mode compilation proved `ex2.approx.ftz.f32` before repeating full
build/link/import. Separate diagnostic script mistakes (bare remote `python`
PATH and assuming an output-only case had a state-error entry) likewise belong
to the harness, not the device. They must not be conflated with candidates
correctly rejected for C7512 serialization or excess spill allocation.
